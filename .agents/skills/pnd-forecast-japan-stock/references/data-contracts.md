## 1. 読取専用境界

市場データ収集が公開する情報GETだけを使う。現行実装で登録状態を変更するのは`PUT /register`、`PUT /unregister`、`PUT /unregister/all`だけである。これらと注文、取消、口座・建玉操作を呼ばない。直接サーバーへ要求せず、市場データ収集経由で取得する。

## 2. 現在価格の優先順位

1. 日付、市場状態、取得時刻を検証したKabusControllerの板
2. J-Quantsの当日または最終取引日公式終値
3. 遅延と商品種別を確認できる外部価格

休場中は「現在値」ではなく「最終取引日終値」と書く。板の`CurrentPriceTime`は最終約定時刻、`upstream_fetched`と`collected_at`は取得時刻である。`is_stale=null`を新鮮とみなさない。

`Buy1`は最良買い気配、`Sell1`は最良売り気配である。トップレベルの`AskPrice=Buy1`、`BidPrice=Sell1`は一般的な名称と逆なので使用しない。

取引時間中は価格・板を出力直前に再取得する。5分を超えた取得値は原則再取得し、現在値が分析中に2%または0.5ATR以上動いたら価格案を作り直す。最終約定が古くても、取得直後の正常な両側板があれば、約定鮮度と板取得鮮度を別評価する。

## 3. コード接続

次のキーを正規化レコードへ保持する。

- 表示用4桁・英数字コード
- J-Quants用5桁コード
- EDINETコード
- 正式社名、法人番号、市場区分
- 外部サービス用ティッカー

5桁コードを機械的な末尾0付与だけで作らず、J-QuantsマスターまたはEDINETのコード検索で照合する。Kabuの省略社名をEDINET検索の主キーにしない。

## 4. J-Quants

J-Quantsは公式の日次・週次データであり、リアルタイムではない。`collected_at`が現在でも、返却された`Date`や基準日を現在扱いしない。

| データ | 主な時点 | 扱い |
|---|---|---|
| 日足 | 取引日ごと、当日終値後 | OHLCV、売買代金、調整、ATR |
| 財務サマリー | 開示日次、速報・確報あり | EDINETと期間・提出時刻を照合 |
| 信用残 | 週次 | 急落当日の需給と呼ばない |
| 空売り残高 | 計算日・公表日 | 各主体の最新行だけを使う |
| 業種空売り比率 | 33業種 | 個別銘柄へ帰属させない |

日足の`C`、`Vo`、`Va`がnullの無商い銘柄を0へ変換しない。分割・併合では調整済み価格、`AdjFactor`、権利落ちフラグを確認する。

## 5. EDINET DB・政策DBの利用優先度

固定件数で呼出しを禁止せず、結論への影響で次の優先度を付ける。

| 優先度 | 判定 | 主な例 |
|---|---|---|
| A（高優先） | 結論、価格レンジ、撤退条件を変える一次確認 | EDINETの最新決算、業績修正、希薄化、会計・統治、決算予定 |
| B（条件付き） | 重要性が先に検出され、追加確認でシナリオが変わり得る | EDINETの詳細財務・セグメント・KPI、政策DBの直接性確認 |
| C（低優先） | 結論を変えない網羅探索・背景補足・重複取得 | 政策テーマの総当たり、確認済み文書の再取得 |

- EDINET DBのA項目を政策DBの背景補足より優先する。
- 政策DBは具体政策が投資仮説の中核である場合に優先度を上げる。
- batchを優先し、同一実行中に同じ会社・期間・文書を再取得しない。
- 回答に各DBの利用優先度、使用・未使用の理由、未確認の影響を表示する。

## 6. EDINET DB

証券コードからEDINETコードを解決し、次の順で使う。

1. 決算・イベント・決算予定で最新開示を把握する。
2. 財務で複数年比較する。
3. 必要時だけセグメント、受注残、KPI、IR文書を深掘りする。
4. 重要判断は原本URL、引用箇所、提出日時へ戻る。

単一エンドポイントが空でも「開示なし」としない。決算、イベント、IR文書は収録範囲が異なる。`sourceType`、`derivationMethod`、`confidence`を保持し、LLM抽出・差分算出・四半期単独値を原本値と混同しない。

## 7. ニュース取得ツール

毎回`list_sources`相当で稼働状況を確認する。`enabled=true`かつ記事0件は「稼働未確認」であり「材料なし」ではない。

検索語は最大5語ANDのため、正式名、株式会社除去名、略称、英名、表示コードを別クエリにする。5桁コードをそのまま検索しない。見出しに会社固有語・表示コードがあるか、局所本文で会社名とコードの両方が一致した結果だけ採用する。

重複は`source_id + external_id`を基本キーとし、同一キーの最新版を残す。`canonical_url`だけで消さない。異ソースの同一事象はイベント群へ束ね、一次情報を主、Reuters等を市場解釈として残す。

JPXマーケットニュースは売買停止、監理・整理、上場廃止、値幅制限等のゲートに使う。会社IR・TDnetの網羅経路ではないため、決算・希薄化・自社株・M&AはEDINET DBで確認する。

## 8. 政策DB

政策DBは、会社へ直接結び付く案件の仮説検証に使う。次を別レコードとして保持する。

- エンドポイント名
- テーマ・事業名
- 対象年度・期間
- `amount_basis`
- 企業受領額かプロジェクト総額か
- 子会社・下請けを含むか
- 原典

同名テーマでもエンドポイント間の母集団が異なることがある。会社政策額、award型公的資金、行政事業レビュー総額、テーマ集計を横断加算・比率化しない。古い少額案件や単なるテーマ所属を株価触媒へ加点しない。

## 9. 不整合時の扱い

主要価格が二源で0.5%以上異なる、取引日が異なる、訂正開示がある場合は再取得する。売上・利益・EPSは単位、連結範囲、累計・単独、株式数、決算期を揃えて算術検算する。

EDINETとJ-QuantsのEPSだけが不一致になる例がある。差を平均せず、原本と計算式を確認する。解消しなければEPS依存の点目標を停止し、レンジを広げ、確信度を下げる。
