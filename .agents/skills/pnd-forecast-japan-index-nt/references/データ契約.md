# データ契約と取得規則

## 1. 情報源の役割

| 情報源 | 主な用途 | 現在値として使えるか | 主な制約 |
|---|---|---|---|
| 市場データ収集／KabusController | 先物・OPの現在板、実登録限月、銘柄解決 | 板条件と時刻を満たせば可 | 情報取得だけを使い、登録・発注は禁止 |
| 市場データ収集／225225.jp | 現物指数、海外、為替、NT、業種、寄与度 | 市場状態と系列時刻を確認した補助値 | 二次配信。執行価格には使わない |
| 市場データ収集／J-Quants | 公式日足、財務、投資主体、信用、OP日足・建玉 | 不可 | 日次・週次。データ自身の対象日が必要 |
| ニュース取得ツール | 直近材料、市場解釈、マクロ調査、JPXイベント | 価格には使わない | 保存記事の網羅性と取得遅延を確認 |
| EDINET DB | materiality gate通過後の主要構成銘柄イベントの一次確認 | 価格には使わない | 重大イベントでは政策DBより優先 |
| 政策DB | materiality gate通過後の指数・NT判断の中核政策確認 | 価格には使わない | 一般テーマ探索には使わない |

## 2. 市場データの取得順

1. `datalist`で実行時の契約を確認する。
2. `markets_calendar`と日本時間で市場状態を確定する。
3. `nt_pair_symbol_resolver`で同一の明示限月を解決する。
4. `future_registrations`、`future_market_data`、`symbol_market_data`または`arbitrary_board_snapshot`で板を取る。
5. 225225.jpの`current`、`chart`、`japan_contributors`、`japan_industries`、`fx_rates`を必要に応じて取る。
6. J-Quantsの`indices_bars_daily`、`indices_bars_daily_topix`、`equities_investor_types`、信用・空売り、`derivatives_bars_daily_options_225`を取る。
7. ニュース取得ツールで直近材料と重要イベント予定を確認し、ここまでの情報でEDINET DB・政策DBのmateriality gateを判定する。
8. gateを通った場合だけEDINET DBまたは政策DBを呼ぶ。重大な構成銘柄イベントはEDINET DBを優先し、batchを優先して、取得済み結果を以後の全工程で再利用する。
9. `option_registrations`、`option_chain_snapshot`、`option_market_data`でOPを検証する。利用可能なら読取専用の登録状態データも取る。
10. 最終判断後、回答直前に先物両脚の板を再取得する。

固定した名前が`datalist`に存在しない場合は、似た名前を推測して呼ばない。現在の一覧から同目的のデータセットを選び、代替できなければ欠損を表示する。

## 3. 時刻を分離する

| フィールド | 意味 | 禁止する読み方 |
|---|---|---|
| `as_of` | 分析基準時刻 | 全データの生成時刻 |
| `upstream_fetched`／`collected_at` | スナップショット取得時刻 | 最終約定時刻 |
| `CurrentPriceTime` | 最終約定時刻 | 板の更新時刻 |
| 日足`Date` | 公式取引日 | 夜間の現在値 |
| `published_at` | 記事・開示の公表時刻 | 収集時刻 |
| `fetched_at` | 保存システムの取得時刻 | 公表時刻 |

- `is_stale:null`は「新鮮」ではなく判定不能とする。
- `market_state:"unknown"`は開場中ではない。
- 集約の`age_seconds`だけで判断せず、使用する各行を確認する。
- 取引中は`upstream_fetched`が実行直近であることを確認し、古ければ再取得する。再取得しても現在性を確認できなければ入口を保留する。
- 両脚のスナップショット時刻差が大きければ再取得する。最終約定が5分超なら警告、10分超または無出来高なら流動性評価を下げるが、直近取得した両側板まで古いとは断定しない。

## 4. 板の正規化

現行のKabusController応答では、一般的な名称感覚と逆向きのトップレベルフィールドがある。常に次を正とする。

```text
Buy1  = 最良買い気配
Sell1 = 最良売り気配
```

板の最低条件は次のとおり。

1. `Buy1.Price > 0`
2. `Sell1.Price > 0`
3. `Sell1.Price >= Buy1.Price`
4. 必要枚数に対する数量を確認できる
5. スプレッドが想定利益を食い尽くさない
6. 限月、取引最終日、市場状態が取引案と一致する

## 5. J-Quants更新契約

公式性は高いがリアルタイムではない。更新予定時刻は保証ではなく、必ず返却された対象日を優先する。

| データ | 主な頻度・更新目安 | 扱い |
|---|---|---|
| 株価四本値 | 日次、16:30頃 | 引け後の公式日足 |
| 上場銘柄一覧 | 日次、17:30頃・翌営業日8:00頃 | 商品区分・コード正規化 |
| 財務情報 | 日次、18:00頃速報・24:30頃確報 | 開示日時と速報・確報を確認 |
| 決算予定 | 日次、10:00頃 | イベント日程 |
| 日々公表信用残 | 日次、16:30頃 | 対象日付き需給 |
| 信用週末残高 | 週次、第2営業日16:30頃 | 基準週末日付き需給 |
| 投資部門別 | 週次、第4営業日18:00頃 | 対象週と公表日付き需給 |
| 空売り残高報告 | 日次、17:30～19:00頃 | 計算日と公表日を分離 |
| デリバティブ建玉 | 日次、21:15頃 | 過去日次の建玉・PCR補助 |

`collected_at`が現在でも、対象日が古いデータを現在値・現在需給と呼ばない。更新前の当日欠損は直ちに障害としない。異なる基準日の指数日足をNT履歴へ混ぜない。

## 6. OPの有効性ゲート

次をすべて満たす場合だけ、OPを方向・ボラティリティの補助材料にする。

1. 実登録一覧の`derivMonth`が、対象先物と整合する取引可能限月である。
2. 取引最終日前であり、SQを通過した旧限月ではない。
3. 登録処理の状態、完了時刻、基準価格・時刻・モード、登録最小・最大価格を取得できる場合は表示する。
4. 現在先物が登録範囲内で、現在先物に最も近い登録ストライクをATMとする。
5. ATMと少なくとも上下2ストライクのCall・Putが欠損していない。
6. 使用する全契約に正の`Buy1`・`Sell1`があり、売り気配が買い気配以上である。
7. `upstream_fetched`等の板スナップショットが現在性を持つ。
8. スプレッドと板数量が分析用途に耐える。

次を区別する。

```text
登録カバレッジ完全 ≠ 両側板あり
CurrentPriceがnull ≠ 板なし
CurrentPriceTime   ≠ 板取得時刻
IVが非null         ≠ 現在板から逆算したIV
CalcPriceが非null  ≠ 約定可能価格
resolver成功       ≠ Controller板取得成功
```

生のIVは由来が不明なら参考値に限定する。ライブIVを用いるなら、Call・Putの板中値、原資産、残存時間、金利、配当仮定を揃えて再計算する。リアルタイムチェーンに建玉がなければPCRを作らず、J-Quantsの日次建玉を対象日付きで別表示する。

## 7. ニュース・EDINET・政策DB

市場データとニュースで候補を絞ってから、EDINET DB・政策DBのmateriality gateとA/B/C優先度を判定する。結論への重要性と代替不能性で利用を決める。

| 優先度 | 判定条件 | 行動 |
|---|---|---|
| A（高優先） | 一次確認の結果が結論、撤退条件、または確信度を変え得る | 必要なDBを使い、一次情報を確認する |
| B（条件付き） | 安価な市場データ・ニュースで具体的材料を検出し、追加確認が有用 | 重要性と代替不能性を確認して使う |
| C（低優先） | 網羅探索、背景補足、または結果が結論を変えない | 呼ばず、省略影響を記録する |

### ニュース

- 最初に取得対象一覧を確認する。`enabled=true`でも記事0件なら稼働確認済みとみなさない。
- Reutersは場中の市場解釈、大和総研・日本総研はマクロ仮説、JPXマーケットニュースは指数・取引所イベントに使う。
- `日経平均`、`日経225`、`TOPIX`、`ＴＯＰＩＸ`、`円相場`、金利、業種名を分けて検索する。最大5語のAND条件へ詰め込まない。
- 同じ記事は`source_id + external_id`を基本キーとし、改訂は最新を残す。JPXの異なるイベントをURLだけで削除しない。
- 記事0件を材料なしとせず「ニュース経路では未確認」とする。

### EDINET DB

- 日経寄与度上位またはTOPIXウェイト上位であるだけでは呼ばない。
- 市場データまたはニュースで主要構成銘柄の具体的な決算、業績修正、希薄化、還元、M&A等を検出し、一次確認により結論、確信度、または撤退条件が変わり得る場合だけmateriality gateを通す。
- 呼出前に「検証する事実」「結論への想定影響」「取得済み結果で代替できない理由」を各1行で整理する。いずれかが具体化できなければ呼ばない。
- 重大な構成銘柄イベントの一次確認をA（高優先）とし、政策DBの調査より先に行う。複数銘柄・文書を一度に指定できるbatch機能を優先し、同じ文書・イベントの結果を別endpointで取り直さない。
- ある取得経路が空でも別経路に開示があるため、単一ツールの空を開示なしと断定しない。
- 数値差は対象期間、連結・単体、会計基準、単位、加重平均株式数を確認し、解消できなければ併記して低信頼とする。
- `get_fair_value`を価格目標、割安・割高、売買推奨に使わない。

### 政策DB

- 市場データまたはニュースで直近の具体的政策を検出し、それがNTまたは指数判断の中核となる場合だけmateriality gateを通す。
- 呼出前に「具体政策」「判断の中核となる理由」「取得済み結果で代替できない理由」を各1行で整理する。政策テーマの一般調査には呼ばない。
- 具体政策が指数・NT判断の中核となる場合をA（高優先）またはB（条件付き）とし、batchを優先して同一結果を再利用する。重大な構成銘柄イベントとの比較ではEDINET DBの一次確認を先に行う。
- 政策テーマの存在だけで指数方向を決めない。公表時期、原典、企業・業種への直接性を確認する。
- 異なるendpointや`amount_basis`の金額を合算・除算しない。公的支出を企業の売上や利益へ読み替えない。
- 日中の短期予測には低ウェイト、5～20営業日の構造要因に使う。
- 該当なしは減点せず「観測された直接的政策材料なし」とする。

### 利用判断の監査表示

- EDINET DBと政策DBについて、利用判断、A/B/C優先度、確認対象、利用または省略による影響を回答の「データ鮮度と欠損」および「根拠資料」に必ず表示する。
- materiality gateを通さず呼ばなかった場合は「未使用」と理由を表示し、「取得不能」と区別する。
- 一度得た結果はスコア、シナリオ、撤退条件、根拠資料で共有し、表示のためだけに再取得しない。

## 8. 欠損時の扱い

- KabusController板が取れない: 指数観測は継続できるが、具体的な入口・枚数は保留する。
- 225225.jpが取れない: KabusController板とJ-Quants履歴で分析し、業種・寄与度の確信度を下げる。
- J-Quants当日分が未更新: 最新対象日を表示し、履歴・遅行需給として使う。
- ニュースが0件: 材料なしとは断定せず、ニュース確認不能とする。
- materiality gate通過後にEDINET DBまたは政策DBが取れない: 未確認となった証拠項目を0点とし、推測で補わない。gate不通過による意図的な未使用は取得不能と扱わず、市場データ・ニュース等で確認した範囲を記録する。
- OPゲート不合格: OPをスコアから外す。指数分析全体を自動停止しない。
