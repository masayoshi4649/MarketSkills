# データ契約・取得順・鮮度規則

## 1. データ取得境界

- 市場データ、ニュース、EDINET DB、政策DB、公開Webの読取専用機能だけを使う。
- 市場データMCPと`datalist`が実行環境に存在する場合は、provider、dataset、引数、読取契約を確認する。固定名を推測して呼ばない。
- `datalist`または固有providerが存在しない場合は、公式Web、J-Quants、利用可能な別の読取providerへ切り替える。ライブ両脚板を取得できない場合、ファンダメンタルズ調査は続けても入口、枚数、現在板ベース確率は保留する。存在しないツール名を呼ばない。
- 公式カレンダー、商品仕様、一次論文は読取専用の検索・ブラウザで確認してよい。ローカル計算スクリプトへネット取得を混ぜない。
- Polymarketは公開市場・板・価格を分析材料として使う。
- 具体的な板、時刻、限月、取引最終日を検証できないときは、入口と枚数を保留する。

## 2. 情報源の役割

| 情報源 | 主な用途 | 現在値としての扱い | 主な制約 |
|---|---|---|---|
| KabusController | 同一限月の先物・OP板、銘柄解決、登録済み窓 | 板条件と時刻を満たせば執行アンカー | `Buy1`と`Sell1`を使い、板時刻を検証する |
| 市場データMCPの225225.jp系provider | 現物指数、海外市場、為替、国債利回り、商品、暗号、NT、業種、寄与度 | 系列時刻と商品種別を確認した補助値 | 二次配信。入口価格と確率の単独根拠にしない |
| J-Quants | 取引カレンダー、指数日足、投資部門別、信用・空売り、OP日足・建玉 | 現在板には使わない | 日次・週次。データ自身の対象日が必要 |
| 公式経済カレンダー | 日銀、GDP、CPI、雇用、FOMC、米国指標等の予定 | 価格ではない | 日程変更、現地時間、夏時間を再確認 |
| ニュース取得ツール | 直近材料、市場解釈、イベント発見 | 価格には使わない | 取得遅延、記事0件、表記揺れを監査 |
| Polymarket公開市場 | 政策・選挙・地政学等の条件付きシナリオ事前情報 | 日本株価格には使わない | 判定条件、期限、流動性、スプレッドが必要 |
| EDINET DB | 主要構成銘柄イベントの一次確認 | 価格には使わない | materiality gate通過後だけ使う |
| 政策DB | 具体政策と指数・業種の直接関係 | 価格には使わない | 一般テーマ探索に使わない |
| JPX・日経指数公式 | 商品仕様、取引最終日、SQ、日経平均VI | 仕様・指数定義 | 実行時の板とは別物 |

ユーザーが「NK225jp」「Nikkei225jp」等と呼んだ場合でも、MCP上の実provider名と返却された`source_url`を正とする。ブランド名だけで`225225.jp`系providerと同一だと決めつけない。

## 3. 取得順

### 3.1 共通アンカー

1. 利用可能な読取能力を列挙する。`datalist`があれば全providerとdatasetを確認し、なければ公式Web・J-Quants・利用可能な読取providerの範囲を記録する。
2. J-Quants取引カレンダー、日本時間、JPXセッションから現物・日中先物・ナイト先物・休場を判定する。`market_state:"unknown"`を開場中とみなさない。
3. `nt_pair_symbol_resolver`等の調査済みresolverで、TOPIX mini、日経225 mini、日経225 microの同一四半期限月を解決する。
4. 実行時に契約確認できた板取得機能で両脚を近接時刻に取る。日経・TOPIXの商品ID、四半期限月、取引最終日、公式の最終取引可能時刻、個別板時刻、Buy1・Sell1、各数量を保存し、古い方の板時刻をTTL起点にする。
5. JPX公式の取引最終日、SQ、商品乗数を再確認する。

### 3.2 並列取得するファンダメンタルズ系統

- 225225.jp系の`catalog`、`current`、`chart`、`fx_rates`、`us_equities`、`crypto_assets`等から、実行時に存在する系列を選ぶ。
- 公式経済カレンダーから、現在以後D5までの日本、米国、必要に応じて欧州・中国の発表を取る。
- ニュースを指数、為替、金利、主要業種、主要構成銘柄、政策、地政学に分けて検索する。
- 主要構成銘柄の具体的イベントが結論を変え得る場合だけEDINET DBを使う。
- 具体政策が結論の中核なら政策DBを使う。
- 関連する公開予測市場がある場合だけPolymarketを検証する。

### 3.3 並列取得する需給系統

- 225225.jp系の`japan_contributors`、`japan_industries`、現物・先物、NT系列を取る。
- J-Quantsの指数日足、投資部門別、信用、空売り、売買内訳、利用可能ならデリバティブ手口・建玉を取る。
- KabusControllerの先物板、ベーシス、スプレッド、数量を取る。
- 日経225 OPの登録窓、Call・Put両側板、日次建玉を別々に検証する。
- SQ、ロール、指数リバランス、配当落ちを確認する。

### 3.4 最終再取得

分析と計算ツールの実行後、回答直前に同一限月の両脚板を再取得する。アンカー、入口、NT倍率、等価枚数、整数構成、端数残存、出口をすべて再計算する。最終再取得後に根拠の方向が変わった場合は確率も再計算する。

## 4. 最低限のデータ台帳

全ての数値証拠に次を持たせる。返却されない項目は`不明`とし、推測しない。

| フィールド | 内容 |
|---|---|
| `provider` | 配信元または公式発表元 |
| `venue` | 取引所、OTC参考値、予測市場等 |
| `instrument_type` | 現物、先物、CFD、利回り、ベンチマーク等 |
| `symbol` | 銘柄・系列識別子 |
| `expiry` | 先物・OPの限月または予測市場期限 |
| `quote_type` | bid、ask、last、mid、fixing、終値等 |
| `source_timestamp` | データ自身の時刻 |
| `fetched_at` | 取得時刻 |
| `delay_status` | ライブ、遅延、日次、週次、不明 |
| `currency`と`unit` | 通貨・単位 |
| `reference_period` | 経済指標、フロー、財務の対象期間 |
| `evidence_key` | 同一事象の重複排除キー |

計算入力の`coverage`には、`news`、`realtime_fx`、`economic_calendar`、`polymarket`、`overseas_markets`、`jgb`、`ust`、`oil`、`gold`、`crypto`、`jquants`、`options`を過不足なく入れる。各項目は`status`、`reason`、24時間以内の`checked_at_jst`を持つ。`used`と`excluded`は`data_as_of_jst`および重複のない1件以上の`source_ids`も必須とする。`data_as_of_jst`は`checked_at_jst`以前でなければならない。複数の公式カレンダー、報道元、取引所を1つの包括IDへ潰さない。

- `used`: 証拠、イベント、シナリオ重み・条件付きモデル、4象限base、NT相対価値・相対σ、日次ドリフト、営業日または変動幅へ利用した。
- `excluded`: 取得したが鮮度、関連性、流動性、二重計上等の理由で不採用にした。
- `unavailable`: 能力不足、認証不足、応答失敗等で取得できなかった。
- `not_applicable`: 関連する市場が存在しないPolymarketだけに許す。

他の項目を`not_applicable`にして確認を省略しない。欠損を中立値へ変換しない。

`used`の最大データ年齢は、リアルタイムFX・暗号・OPが5分、Polymarket・海外市場が15分、原油・金が30分、ニュース・経済カレンダーが24時間、JGB・USTが72時間、J-Quantsが168時間である。より短いprovider TTLがあればそちらを優先する。リアルタイムFX、経済カレンダー、海外市場が全て`used`で、全12項目中5項目以上が`used`の場合だけ、市場横断データ面の分析ゲートを通す。

証拠、イベント、シナリオ重み・条件付きモデル、4象限base、NT相対価値・相対σ、日次ドリフト、営業日、D1～D5の変動幅は`coverage_item`、`source_id`、データ対象時刻を持ち、対応するcoverageが`used`で、`source_id`が`source_ids`に含まれる場合だけ利用できる。逆に`used`とした全coverage sourceは、これらのいずれかで実際に消費しなければならない。証拠は時間減衰後の有効倍率が正、シナリオは重みが正の場合だけ消費と数える。D5まで重要イベントが0件なら、経済カレンダーの確認結果を全0の`neutral_observation`証拠として記録し、架空イベントを作らない。`neutral_observation=true`と非ゼロ方向スコアを併記しない。4象限が全て同じ非ゼロ値の証拠は中心化後に方向差が消えるため拒否し、中立確認は全0だけで表す。

モデル来歴の`source_links`は、モデルID・版、校正版、方式、構造ID、`model_artifact_sha256`、学習データ打切時刻、期限定義・秒数、検証状態と組で保存する。`probability.base_provenance`は現在base予測出力の`prediction_output_sha256`も持つ。期限一致校正側とは方式・モデルID・構造ID・モデル成果物SHA-256を一致させ、現在予測出力SHA-256は転記後の改変検知として毎回再計算する。

これらのSHA-256は転記・内容一致の整合性検査用であり、情報源、モデル成果物、作成者の真正性を証明しない。純計算ツールは入力形式、OS実時計に対する現在性、鮮度を含む時刻関係、数理不変条件を検証する。`status: ok`でも、取得した一次資料・対象時刻・モデル来歴は回答で別途監査可能にする。

12項目外の固有DB・一次資料は`coverage_item: other`とし、トップレベル`other_sources`へ次を登録する。

```text
source_id
source_url_or_document_id
reason
checked_at_jst
data_as_of_jst
max_data_age_hours
```

`checked_at_jst`は24時間以内、`data_as_of_jst`は未来でなく`checked_at_jst`以前、データ年齢は申告した鮮度上限以内とする。証拠等の参照時刻そのものも同じ鮮度上限で検証し、台帳だけ現在へ更新して古い材料を通さない。

## 5. 時刻を分離する

回答と純計算器の日時出力は可能な限りJSTへ変換し、`yyyy/MM/dd HH:mm:ss (JST)`へ統一する。機械入力は夏時間と同一瞬間を監査するため、原timezoneのISO 8601とUTC offsetを保持してよい。発表元原時刻を検証した後、利用者向け出力では`scheduled_at_source_jst`へJST換算し、`source_timezone`と`source_utc_offset`を別項目で残す。原時刻を回答本文の主表示にしない。取引日、限月、学習終了日など時刻を持たない制度上の日付には`00:00:00`を補わず、公式の時刻が別に存在する場合だけ根拠付きJST日時として併記する。

| フィールド | 意味 | 禁止する読み方 |
|---|---|---|
| `as_of` | 分析基準時刻 | 全データの生成時刻 |
| `audit.runtime_now_jst` | 計算時のOS実時計 | 入力側が自己申告する現在時刻 |
| `upstream_fetched`・`collected_at` | スナップショット取得時刻 | 最終約定時刻 |
| `CurrentPriceTime` | 最終約定時刻 | 板更新時刻 |
| 日足`Date` | 公式取引日 | 夜間の現在値 |
| `published_at` | 記事・開示の公表時刻 | 収集時刻 |
| `fetched_at` | 保存システムの取得時刻 | 公表時刻 |
| `scheduled_at` | 予定公表時刻 | 実際の公表時刻 |

- `is_stale:null`は「新鮮」ではなく判定不能とする。
- `as_of`はOS実時計より30秒を超えて未来、または120秒を超えて過去なら分析候補を保留する。OS実時計が入口板・予測の絶対有効期限以後の場合も保留し、計算結果を新しい現在判断として使わない。
- 最終約定が5分超なら警告、10分超または無出来高なら流動性評価を下げる。ただし直近取得した正常な両側板まで古いとは断定しない。
- 両脚のスナップショット時刻差が大きい場合は再取得する。
- 海外時刻はIANAタイムゾーンで日本時間へ変換する。原時刻の壁時計・UTC offsetを当日の夏時間規則と照合してからJSTへ変換し、米国・欧州を固定UTC差で変換しない。回答にはJST換算値と`(JST)`を表示し、原timezoneとoffsetは監査情報として分離する。

## 6. 板の正規化

KabusControllerでは次を正とする。

```text
Buy1  = 最良買い気配
Sell1 = 最良売り気配
```

トップレベルの`AskPrice`・`BidPrice`から方向を推測しない。最低条件は次のとおり。

1. `Buy1.Price > 0`
2. `Sell1.Price > 0`
3. `Sell1.Price >= Buy1.Price`
4. 必要枚数に対する数量がある
5. スプレッドと想定スリッページが期待幅を食い尽くさない
6. 限月、取引最終日、セッションが一致する

NTの申告往復コストは、少なくとも`日経ask-bidの中値比 + TOPIX ask-bidの中値比`以上にする。手数料と追加スリッページはその上へ加える。`last_trading_session_end_jst`は現在セッション終了と別に[JPX立会時間](https://www.jpx.co.jp/derivatives/rules/trading-hours/)から保存し、現行ツール版では15:45 JSTへ固定する。4象限の予測有効期限とD5はNT推奨の有無にかかわらず共通限月のこの最終取引可能時刻を越えてはならない。D5を越える予測期限を使うならイベント探索期間も同じ時刻まで延ばし、現実装ではD5を上限とする。

## 7. リアルタイム為替と市場横断データ

少なくとも次を確認し、取得不能も明記する。

| 分類 | 優先して見る系列 | 主な伝達経路 | 誤用防止 |
|---|---|---|---|
| 為替 | USD/JPY、必要時EUR/JPY・ドル指数 | 輸出採算、輸入物価、海外利益換算 | 日付なし時刻や単一venueを市場全体と呼ばない |
| 日本金利 | JGB 2年・10年・超長期、2s10s等 | 銀行、割引率、円、政策期待 | 財務省公表値はリアルタイムでない |
| 米国金利 | UST 2年・10年、実質金利 | 世界割引率、USD/JPY、半導体・成長株 | 日次カーブをライブ値と呼ばない |
| 海外株 | S&P 500、Nasdaq、SOX、Dow、対応先物 | 日本夜間、半導体、景気敏感 | 現物終値・先物・CFDを混ぜない |
| 原油 | WTI・Brentの明示限月 | 日本の輸入コスト、資源・商社 | スポットと先物、異限月を混ぜない |
| 金 | 金先物または明示fixing | 実質金利、ドル、リスク回避 | LBMA fixingをライブスポットと呼ばない |
| 暗号 | BTC・ETHの明示venueまたは複数会場指数 | 24時間リスク選好・流動性の補助 | 株価の原因と断定しない |

225225.jp系providerの系列は、実行時の`catalog`で現物・先物・CFD・利回り・商品・暗号を区別する。`chart`は期間を先に限定し、間引かれた全期間点を直近点と誤認しない。

為替、海外株、金利、原油、金、暗号は全て確認対象だが、同じ世界的リスクオン・オフ事象を6件の独立材料として加点しない。共通イベントを1つの`evidence_key`へまとめ、各市場は反応の整合確認に使う。

公式の遅行データ例は[日銀外国為替相場](https://www.boj.or.jp/en/statistics/market/forex/fxdaily/index.htm)、[財務省JGB金利](https://www.mof.go.jp/english/policy/jgbs/reference/interest_rate/index.htm)、[米財務省金利統計](https://home.treasury.gov/policy-issues/financing-the-government/interest-rate-statistics)、[EIA原油データ](https://www.eia.gov/opendata/documentation.php)である。現在値の代替ではなく、単位・日付・方向の照合に使う。

## 8. 経済指標カレンダー

### 8.1 公式発表元

最低限、D5までに該当する次の公式日程を確認する。

- 日本銀行の[リリース予定](https://www.boj.or.jp/en/about/calendar/index.htm)と[金融政策決定会合](https://www.boj.or.jp/en/mopo/mpmsche_minu/)
- 内閣府の[GDP公表予定](https://www.esri.cao.go.jp/en/sna/kouhyou/kouhyou_top.html)
- 総務省の[CPI公表予定](https://www.stat.go.jp/english/data/cpi/1582.html)と雇用統計
- 財務省の貿易統計、証券投資、国債入札予定
- 米連邦準備制度の[FOMC日程](https://www.federalreserve.gov/monetarypolicy/fomccalendars.htm)
- 米BLSの[公表予定](https://www.bls.gov/schedule/)、米BEAの[公表予定](https://www.bea.gov/news/schedule/)
- 必要時にECB、Eurostat、中国国家統計局、EIA、IEA、OPECの公式予定

### 8.2 保存する項目

```text
event_id
title
coverage_item
source_id
source_url_or_document_id
source_timezone
checked_at_jst
scheduled_at_source
scheduled_at_jst
window_start_jst
window_end_jst
reference_period
release_status: scheduled / preliminary / revised / conditional / market_session
occurrence_probability
occurrence_basis_type: fixed_schedule / official_condition / verified_prediction_market
resolution_verified（verified_prediction_market時）
expiry_aligned（verified_prediction_market時）
liquidity_verified（verified_prediction_market時）
spread_verified（verified_prediction_market時）
consensus_status: used / unavailable / not_applicable
consensus_source（used時）
consensus_checked_at_jst（used時）
previous_value
official_source
```

- 公式発表元は市場予想を通常提供しない。第三者コンセンサスを使うなら提供元と取得時刻を分ける。
- 予定、予想、前回、実績、改定値を混ぜない。
- 予定は分析前24時間以内に公式元を再確認する。確認時刻が古いイベントを変動窓や期限計算へ使わない。
- `event_id`は前後空白除去・大文字小文字正規化後も一意にし、`materiality_threshold`は0.35へ固定する。
- `release_status`が`scheduled`、`preliminary`、`revised`または`market_session`なら`occurrence_probability=1`とする。条件付き事象だけを公式条件または検証済み予測市場から0～1で置く。
- `conditional`かつ公式条件を根拠にする場合は`occurrence_basis_type=official_condition`とし、確認済み状態を0または1で置く。予測市場価格なら`coverage_item=polymarket`、`occurrence_basis_type=verified_prediction_market`とし、判定規則、期限整合、流動性、スプレッドの4検証フラグを全て真にする。ニュース記事だけから任意確率を置かない。
- 日程は分析直前に再確認する。日付のみで時刻不明なら安全側のイベント窓にする。
- 同じイベントの速報と改定を別の独立材料として重複加点しない。
- 入力の`scheduled_at_source`は原時刻のUTC offsetを含むISO 8601とし、そのoffsetが`source_timezone`のIANA規則と当日一致することを先に検証する。`scheduled_at_jst`はJST変換とし、同じ瞬間であることを検算する。JST側は候補窓内に置く。純計算器の出力では原壁時計を再掲せず、`scheduled_at_source_jst: yyyy/MM/dd HH:mm:ss (JST)`、`source_timezone`、`source_utc_offset`へ分離する。`previous_value`が非該当でも空欄にせず`not_applicable`と記録する。
- コンセンサスを使う場合、`consensus_checked_at_jst`は分析時刻以前かつ24時間以内とする。
- `checked_at_jst`をイベントのデータ対象時刻としてcoverageまたは`other_sources`へ結び付ける。Polymarketイベントへ経済カレンダーの鮮度上限を流用しない。
- `coverage_item: other`のイベントは`source_url_or_document_id`を`other_sources[source_id]`の登録原典と一致させる。

## 9. Polymarket

市場データMCPにPolymarket providerがある場合、`search`、`events`、`event`、`markets`、`market`、`order_book`、`token_price`、`price_history`、`open_interest`、`live_volume`、`spread`等の読取専用データだけを使う。実際の一覧は`datalist`を正とする。

採用前に次を全て検証する。

1. 質問文と日本株シナリオの因果関係が具体的である。
2. 判定期限が予測期限またはD1～D5と整合する。
3. `resolutionSource`と判定規則が明確である。
4. `active`、`closed`、最終更新時刻を確認できる。
5. Yes/Noまたは複数結果と価格の添字対応が正しい。
6. bid・ask、仲値、スプレッド、板数量、出来高、流動性を確認できる。
7. 価格持越しや休止状態でない。

公式仕様は[市場データ概要](https://docs.polymarket.com/market-data/overview)、[価格と板](https://docs.polymarket.com/concepts/prices-orderbook)、[判定仕様](https://docs.polymarket.com/concepts/resolution)で確認する。

- 価格は市場参加者の条件付き価格であり、校正済み実現確率とは断定しない。
- 日本株の上昇・下落確率へ直接置換しない。該当シナリオの発生重みとしてだけ使う。
- スプレッド、流動性、判定リスクが悪ければ`source_quality`を下げるか不採用にする。
- 同じ地政学材料をニュースとPolymarketで二重加点しない。
- 該当市場がないことを確率0と扱わない。
- シナリオ重みへ使う場合、各排他的シナリオに`coverage_item`、`source_id`、`observed_at_jst`、正の重み、排他・網羅確認、集合共通の`partition_definition_id`を持たせ、Polymarket coverageの利用・鮮度・source包含と一致させる。
- `P(q|s)`には別途`conditional_probability_basis`を持たせ、モデル版・校正版・構造・学習打切・今回の期限・原典を監査する。Polymarketはシナリオ重みの根拠であり、条件付き日本株方向分布の唯一の原典にしない。

## 10. J-Quants

実行時の契約とデータ自身の対象日を正とする。代表的な対象は次のとおり。

| データ | 主な頻度・更新目安 | 用途 |
|---|---|---|
| 指数・株価四本値 | 日次、16:30頃 | 日経・TOPIX同期履歴、分散、相関 |
| 投資部門別 | 週次、第4営業日18:00頃 | 遅行する主体別需給 |
| 売買内訳 | 日次、18:00頃 | 当日売買の補助 |
| 日々公表信用残 | 日次、16:30頃 | 過熱・巻き戻し補助 |
| 信用週末残高 | 週次、第2営業日16:30頃 | 遅行残高 |
| 空売り残高報告 | 日次、17:30～19:00頃 | 計算日付きの個別・集計補助 |
| デリバティブ取引高 | 日次、17:30頃 | 利用可能時の手口補助 |
| 取引参加者別建玉 | 週次、第1営業日15:30頃 | 遅行ポジション補助 |
| 銘柄別建玉 | 日次、21:15頃 | OP・先物建玉、対象日付き |

公式の更新目安は[J-Quants Pro更新時刻](https://jpx.gitbook.io/j-quants-pro-ja/data-update)を確認する。更新時刻は保証ではない。

- `collected_at`が現在でも、対象日が古いデータを現在需給と呼ばない。
- 投資部門別は市場区分別の週間現物集計であり、日経対TOPIX配分ではない。
- 2023年11月以降など公表仕様が変わった系列を、売買別の連続ネットフローとして機械接続しない。
- 訂正データは対象日と公表日を確認し、最新版を採用する。
- J-QuantsのOP日足から現在IVやリアルタイムPCRを作らない。
- D1～D5営業日には`calendar_coverage_item`、`calendar_source_id`、`calendar_data_as_of_jst`、24時間以内の`calendar_fetched_at_jst`を持たせ、データ対象時刻を取得時刻以前にする。J-Quants利用時はcoverageの`jquants`へ結び付ける。
- `calendar_sessions`へ分析翌日からD5までの全暦日を連続して入れ、各日を`is_trading_day`で公式確認する。土日を取引日にせず、そこから導出した最初の5取引日だけを`verified_trading_dates`とする。D5は分析翌日から15暦日以内とし、未来の平日を任意に飛ばさない。
- 各指数・各日の変動幅は`expected_move_source_links`へ1件以上の`coverage_item`、`source_id`、`data_as_of_jst`を保存する。表示用の`expected_move_source`だけで鮮度監査を代用しない。
- 日次方向は`drift_model_provenance`を持ち、非ゼロF/S/E寄与を`drift_attributions`の`evidence_key`／`event_id`と`contribution_bps`へ分解する。帰属合計は申告bpと一致させ、`expected_move_source_links`を方向根拠へ流用しない。
- `major_events`が空の日はイベント方向・イベント増分σをともに0とする。イベント増分σが正なら`event_variance_event_ids`へ当日の重要イベントを1件以上記録する。
- 非対称累積分位を使う場合は`p05 < p16 < 0 < p84 < p95`を必須とし、68%・90%幅を同日の累積σによる正規幅の0.5～2.0倍へ収め、D1からD5へ縮小させない。
- 現在ツールが扱う先物アンカーの呼値は日経225 mini/microが5、TOPIX miniが0.25へ固定する。丸め後は全価格を正値とし、`90%下限 <= 68%下限 <= P50 <= 68%上限 <= 90%上限`かつ両帯を正の幅にする。
- D1～D5の`major_events`は表示名でなく正規化可能な`event_id`配列とする。現在より後かつD5までの重要イベントを、予定時刻以後で最初の対象予測点へ過不足なく割り当て、日経・TOPIXで同一配列にする。

## 11. OP有効性ゲート

次を全て満たす場合だけ、現在OPを分散・歪度の補助へ使う。

1. 実登録一覧の`derivMonth`が取引可能限月である。
2. 取引最終日前で、SQ通過後の旧限月でない。
3. 登録状態、完了時刻、基準価格、基準時刻、登録範囲を確認する。
4. 現在先物が登録範囲内である。
5. ATMと上下複数ストライクのCall・Putがある。
6. 使用契約に正の`Buy1`・`Sell1`があり、逆転板でない。
7. `upstream_fetched`等のスナップショットが現在性を持つ。
8. スプレッドと板数量が分析用途に耐える。
9. コール価格面の単調性・凸性、または採用するIV平滑化の裁定条件を確認する。

次を区別する。

```text
登録カバレッジ完全 ≠ 両側板あり
CurrentPriceがnull ≠ 板なし
CurrentPriceTime   ≠ 板取得時刻
IVが非null         ≠ 現在板から逆算したIV
CalcPriceが非null  ≠ 約定可能価格
resolver成功       ≠ Controller板取得成功
リスク中立分布     ≠ 物理確率・実現勝率
```

リアルタイムチェーンに建玉がなければPCRを作らない。J-Quants建玉は対象日付きの日次補助として別表示する。

## 12. ニュース・EDINET・政策DB

### ニュース

- 最初に取得対象一覧を確認する。`enabled=true`でも記事0件なら稼働確認済みとみなさない。
- Reutersは市場文脈、研究機関はマクロ仮説、JPXは取引所イベントに使う。
- `日経平均`、`日経225`、`TOPIX`、`ＴＯＰＩＸ`、為替、金利、業種を分けて検索する。
- 同じ記事は`source_id + external_id`を基本キーとし、改訂は最新版を残す。
- 記事0件を材料なしとせず「ニュース経路では未確認」とする。

### EDINET DB

市場データまたはニュースで主要構成銘柄の具体的な決算、業績修正、還元、希薄化、M&A等を検出し、一次確認が結論、確率、撤退条件を変え得る場合だけ使う。

呼出前に次を内部整理する。

- 検証する事実
- 結論への想定影響
- 取得済み結果で代替できない理由

重大な構成銘柄イベントは政策DBより先に確認し、batchと結果再利用を優先する。同じイベントをニュースと二重加点しない。`get_fair_value`を目標価格や売買推奨に使わない。

### 政策DB

直近の具体政策が指数またはNT判断の中核になる場合だけ使う。一般的な国策テーマ探索には使わない。公表時期、原典、企業・業種への直接性を確認し、異なるendpointや金額基準を合算しない。短期予測では低ウェイト、D1～D5の構造要因として条件付きで使う。

### 優先度

| 優先度 | 条件 | 行動 |
|---|---|---|
| A | 一次確認で結論、確率、撤退条件が変わり得る | 必要なDBを使う |
| B | 安価なデータで具体的材料を検出し、追加確認が有用 | 代替不能性を確認して使う |
| C | 網羅探索、背景補足、結論を変えない | 呼ばず、省略影響を書く |

回答にはEDINET DB・政策DBそれぞれの利用判断、A/B/C、確認対象、利用または省略の影響を表示する。

## 13. 欠損時の扱い

- KabusController板が取れない: 見通しは記述できるが、入口・枚数・現在NT等価枚数は保留する。
- 225225.jp系が取れない: KabusController、J-Quants、公式資料で継続し、海外・業種・寄与度の欠損を明記する。
- リアルタイムUSD/JPYが取れない: 日次fixingで穴埋めせず、為替感応度を低品質または保留にする。
- J-Quants当日分が未更新: 最新対象日を表示し、履歴・遅行需給としてだけ使う。
- 公式経済カレンダーの時刻が確認できない: 予測期限を安全側へ短縮する。安全な窓を作れなければ保留する。
- Polymarketがない・低流動性: 確率0にせず不採用とし、他のファンダメンタルズ証拠で分析する。
- ニュース0件: 材料なしと断定しない。
- materiality gate通過後のEDINET・政策DBが取れない: 未確認項目を0点とし、推測で補わない。
- OPゲート不合格: OPを方向・分散から外し、J-Quants履歴分散へ切り替える。分析全体は自動停止しない。
- ファンダメンタルズまたは需給ブロックが空: 4象限の生モデル確率と四択制約後比較値を算出保留にする。
- `as_of`がOS実時計より30秒超未来、120秒超過去、または実時計で入口板・予測期限を経過: 計算値は監査用に残しても分析候補を保留し、現在時刻で再取得・再計算する。
- 純計算器の`status: ok`だけで情報源・モデル真正性が確認済みだとみなさない。一次資料・対象時刻・来歴を回答側で監査する。
